# Pactum Witness — нотариус контента

Реальное приложение на примитивах ACP/1, которому не нужны деньги: сервис,
который фиксирует «в момент T этот документ существовал ровно в таком виде» —
подписью, проверяемой офлайн, и журналом, который нельзя переписать задним
числом.

Кому это нужно на практике:

- **журналисты и исследователи** — зафиксировать страницу, письмо или датасет
  до публикации («этот текст был у меня 3 ноября, вот подпись»);
- **юристы и комплаенс** — доказать, что договор/смета не менялись с момента
  подписания, без доверенного нотариуса и без блокчейна;
- **релиз-инженерия** — привязать артефакты к моменту сборки: хеш + время +
  подпись сборщика в одной строке;
- **любые участники ACP** — где нужно «я видел это раньше, чем ты заявил».

Скриншоты подделываются, сторонние веб-архивы централизованы и не дают
криптографической проверки. Witness решает задачу примитивами протокола:
подпись ECDSA P-256, хеш-цепочка SHA-256, честные отказы.

## Модель доверия (читать до продакшена)

- **Чему вы верите.** Открытому ключу нотариуса. Он лежит в каждом приёмнике,
  поэтому проверка не требует сервера и сети — только файл приёмника и знание
  ожидаемого ключа (пин). Доверие к ключу — единственное допущение.
- **Что даёт журнал.** Append-only цепочка: каждая запись содержит хеш
  предыдущей. Переписать историю нельзя, не сломав `verify()`. Повреждённый
  журнал сервис не поднимает (`witness serve` отказывается стартовать).
- **Что даёт checkpoint.** Подписанная голова цепочки, которую сервис
  публикует в хаб (топик `witness.head`). Третьи стороны, сохранившие
  checkpoint, делают задний лист невозможным: даже обладатель сервера не
  перепишет историю так, чтобы она совпала с чужими копиями головы.
- **Что Witness НЕ доказывает.**
  - *Время* — берётся системные часы сервера. Для юридически значимой
    метки времени смотрите RFC 3161 (в roadmap) или публикуйте checkpoint
    наружу как можно чаще.
  - *Первоисточник* — Witness фиксирует содержимое, а не то, кто его
    опубликовал первым.
  - *Защиту от нотариуса* — владелец ключа может подписать задним числом
    всё, что угодно, если никто не хранит checkpoint-ы. Поэтому пин ключа +
    внешние checkpoint-ы — не опция, а часть протокола эксплуатации.

## Быстрый старт

### Локально, без сервера (CI-сценарий)

```bash
pactum witness notarize release.tar.gz --store --note "релиз 1.1.0"
# → JSON-приёмник в stdout; сохраните его рядом с артефактом

pactum witness verify receipt.json --dir witness-data
# → «подпись верна … запись #N найдена в журнале, цепочка цела»
```

`--dir` — рабочая папка нотариуса (журнал, blobs, ключ). Без сервера удобно
для фиксации артефактов в CI: нотаризовать — на этапе сборки, проверять —
на этапе аудита.

### Как сервис (REST)

```bash
pactum witness serve --dir witness-data --listen 0.0.0.0:8090
```

Примеры через curl:

```bash
# нотаризовать файл (сохранить копию в blobs/)
curl -sf -X POST --data-binary @contract.pdf \
  "http://127.0.0.1:8090/notarize?store=1&media=application/pdf&note=contract-v3" \
  | tee receipt.json

# нотаризовать страницу целиком (сервер скачает её сам)
curl -sf -X POST "http://127.0.0.1:8090/notarize/url?url=https://example.org/statement&store=1"

# получить приёмник / проверить / выгрузить журнал
curl -s http://127.0.0.1:8090/receipts/<sha256>
curl -s http://127.0.0.1:8090/verify/<sha256>
curl -s http://127.0.0.1:8090/chain/head          # подписанный checkpoint
curl -s http://127.0.0.1:8090/chain/export        # весь журнал NDJSON
curl -s http://127.0.0.1:8090/blobs/<sha256>      # сохранённое содержимое
curl -s http://127.0.0.1:8090/health
```

## API

| Метод и путь | Что делает | Отказы |
|---|---|---|
| `POST /notarize?store=1&media=…&note=…` | тело = документ → приёмник; идемпотентно (тот же дайджест → тот же приёмник, `duplicate: true`) | `413` тело больше лимита, `429` слишком часто, `400` заметка/media длиннее нормы |
| `POST /notarize/url?url=…&store=1` | скачать URL (лимиты, редиректы вручную, SSRF-щит) и нотаризовать | `400` схема/приватный адрес, `413` страница больше лимита, `502` источник недоступен/ошибка |
| `GET /receipts?limit=&offset=` | листинг журнала | — |
| `GET /receipts/{sha256}` | приёмник по дайджесту | `404` не нотариован |
| `GET /verify/{sha256}` | приёмник + подписанная голова + живая перепроверка | `404` не нотариован, `409` подпись/хеш не сошлись |
| `GET /chain/head` | подписанный checkpoint | — |
| `GET /chain/export` | весь журнал NDJSON (для аудита) | — |
| `GET /blobs/{sha256}` | сохранённое содержимое | `404` не нотариован / «не сохранялось (notarize без store=1)», `409` содержимое на диске не сходится |
| `GET /health`, `GET /` | статус, открытый ключ, мини-справка | — |

CLI-команды: `witness serve`, `witness notarize`, `witness verify`,
`witness checkpoint` (подписанная голова + проверка всей цепочки).

## Формат приёмника

Каноническая строка, которая хешируется и подписывается:

```
witness/1|<witness>|<seq>|<ts>|<content_sha256>|<size>|<media|->|<note|->|<stored>|<prev_hash>
```

- `entry_hash` = SHA-256 этой строки; подпись `ecdsa-p256:<hex>` ставится на
  `entry_hash` (детерминированный RFC-6979 — тот же ключ и поля дают тот же
  приёмник байт в байт);
- `prev_hash` связывает запись с предыдущей — журнал и есть цепочка;
- `witness` — короткий id (`p` + 16 hex) из открытого ключа, так что приёмник
  нельзя «перепривязать» к чужому ключу: несоответствие ловится проверкой.

Офлайн-проверка (без сервера, без сети):

```bash
pactum witness verify receipt.json --dir witness-data --pubkey <130-hex-пин>
```

CLI перепроверяет: форму дайджеста, соответствие `witness` ↔ ключу, подпись,
и (с `--dir`) принадлежность журналу и целость всей цепочки.

## Журнал и хранение

```
witness-data/
├── witness.key.json    # ключ (шифруйте: --passphrase или WITNESS_PASSPHRASE)
├── receipts.jsonl      # append-only журнал приёмников (одна строка = одна запись)
└── blobs/<sha256>      # содержимое, сохранённое с store=1
```

- Журнал — единственный источник истины: при старте проверяется целиком,
  повреждённый файл блокирует старт (обход — `Journal::open_unchecked`
  для восстановления, с громким варнингом).
- Blob-ы сверяются с приёмниками при чтении: подмена на диске ловится.
- Бэкап = скопировать папку целиком. Экспорт журнала — `GET /chain/export`.

## Эксплуатация

### Docker

```bash
docker build -t pactum-witness .
docker run -p 8090:8090 -v witness-data:/data pactum-witness
```

### systemd

```ini
[Unit]
Description=Pactum Witness (content notary)
After=network-online.target

[Service]
User=witness
Environment=WITNESS_PASSPHRASE_FILE=/etc/pactum/witness.pass
ExecStart=/usr/local/bin/pactum witness serve --dir /var/lib/pactum-witness --listen 0.0.0.0:8090 --passphrase-file /etc/pactum/witness.pass
Restart=on-failure
NoNewPrivileges=yes
ProtectSystem=strict
ReadWritePaths=/var/lib/pactum-witness

[Install]
WantedBy=multi-user.target
```

> `--passphrase-file` читает фразу из файла; иначе `WITNESS_PASSPHRASE` из
> окружения или `--passphrase` (избегайте: попадает в историю shell).

### За reverse-proxy

Сам сервис говорит HTTP; TLS terminates на прокси (nginx/Caddy). Не
выставляйте сервис в интернет без rate limit (`--rate-per-min`) и потолка
тела (`--max-mb`).

### Связка с хабом (co-witnessing)

```bash
pactum witness serve --dir witness-data \
  --hub-url http://127.0.0.1:8080 --hub-topic witness.head --checkpoint-every 25
# и у любого участника:
pactum hub subscribe --hub http://127.0.0.1:8080 --topic witness.head --callback http://me.local/witness-head
```

Каждая 25-я запись публикует подписанную голову в хаб: подписчики получают
checkpoint и становятся внешними свидетелями. Не ушёл — журнал громко ругается
в лог и продолжает работать, повтор на следующей границе.

## Честные ограничения

- **Время** — системные часы сервера, без гарантий (см. модель доверия).
- **SSRF-щит** — эвристический: приватные/служебные адреса отвергаются до
  запроса, редиректы проверяются по одному, но DNS rebinding между проверкой
  и соединением остаётся возможен. Для враждебных сетей запускайте сервис в
  отдельном network namespace без доступа к внутренним адресам.
- **Ключ одного нотариуса** — единая точка компрометации. Смягчение: внешние
  checkpoint-ы (выше), а в roadmap — пороговые подписи и RFC 3161.
- **Один процесс, один файл журнала** — как и хаб: масштабирование не входит
  в v1. Бэкапы обязательны.

## Roadmap

1. RFC 3161 timestamp-провайдер (внешняя метка времени) как второй якорь.
2. Пороговая подпись (m-of-n нотариусов) для приёмников.
3. Git-якорь: checkpoint в подписанном теге репозитория.
4. Квота на blobs и GC-политика для старых копий.
